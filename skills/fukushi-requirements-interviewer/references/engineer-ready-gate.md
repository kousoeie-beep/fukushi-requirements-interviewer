# エンジニア引き渡し完成条件

最終成果物を作る前と、重要な回答を得た後に参照する。目的は文書を長くすることではなく、エンジニアが推測せずに見積もり・設計・実装・試験へ進める状態を作ることである。

## 文書状態

最終文書の冒頭に、必ず次のいずれかを表示する。

- `ENGINEERING_READY`：すべての必須ゲートを満たし、未解決事項が実装着手を妨げない。
- `CONDITIONALLY_READY`：実装可能な範囲が明確で、残件には責任者・確認方法・期限があり、その残件に依存する部分を着手しない条件が明記されている。
- `DRAFT_NOT_READY`：推測が必要、重大な矛盾がある、または必須ゲートが欠けている。

`完璧`、`完成`、`確定`、`そのまま実装可能`と表現してよいのは `ENGINEERING_READY` の時だけにする。質問数を消化したことや、文章量が多いことを完成根拠にしない。

## 必須ゲート

### G1 目的・範囲

- 解決する問題、影響を受ける人、現在の影響が具体的。
- 最初に作る範囲と、今回は作らない範囲が明記されている。
- 成功指標に現状値、目標値、測定方法、責任者がある。
- 優先度が `必須`、`できれば`、`後続` に分かれている。

### G2 業務フロー

- 各主要業務の開始、担当、参照、手順、判断、引き渡し、確認、完了が分かる。
- 改善前と改善後の流れが比較できる。
- 欠席、誤入力、差し戻し、遅延、重複、通信不可等の重要例外がある。
- 最終的な業務判断者と、システムが補助する範囲が分かる。

### G3 機能要件

- 各要件に一意な `FR-xxx` がある。
- 1要件1動作を原則とし、利用者、開始条件、入力、処理、結果、業務ルール、例外がある。
- 必須要件には確認責任者と根拠がある。
- 曖昧語が測定可能・観察可能な表現へ変換されている。
- 要件間の依存関係と、対象外が分かる。

### G4 画面・操作

- 必要な画面・帳票・通知の一覧と目的がある。
- 役割別に、閲覧・作成・編集・確定・差し戻し・取消の可否が分かる。
- 必須入力、入力確認、空状態、エラー、処理中、完了、利用不可時の振る舞いが分かる。
- 主な画面遷移または操作フローがある。
- スマホ、タブレット、PC、共有端末等の対象が分かる。

### G5 データ

- 主要な情報の項目名、意味、入力元、必須性、形式、選択肢、見る人、直す人が分かる。
- 正しい情報とみなす場所、重複・不一致時の扱いが決まっている。
- 個人情報・要配慮情報等の区分、保存期間、訂正、削除、履歴が分かる。
- 過去情報を移す場合、対象、件数、照合、失敗時の扱いがある。

### G6 既存システムとの情報受け渡し

- 対象の製品・帳票・ファイルと管理者が分かる。
- 受け渡す情報、方向、タイミング、頻度、起点、正本が分かる。
- 失敗、重複、再実行、照合、手動代替の扱いがある。
- 接続方法など技術確認が残る場合、確認先・資料・期限がある。

### G7 情報管理・安全

- 誰が何を見て、書き、確定し、訂正できるかが役割別に定義されている。
- 入社、異動、退職、端末紛失、誤送信時の扱いがある。
- いつ誰が何を行ったか残す対象がある。
- 復元、保存、削除、障害時の連絡・代替手段がある。
- 制度・請求・安全・個人情報に関わる判断の責任者と根拠がある。

### G8 AI利用

AIを使わない場合は `対象外` と明記する。使う場合は次が必要。

- 入力、出力、利用目的、利用してはいけない情報。
- 入力されていない内容を付け加えない等の禁止事項。
- 人が確認・修正・確定する箇所と、外部送信前の確認。
- 誤り・不適切出力の検知、停止、報告、再開判断。
- 正常例、境界例、禁止例を含む評価方法と合格基準。

### G9 品質・運用

- 利用者数、事業所数、件数、繁忙時、利用時間帯がある。
- 待てる時間、同時利用、利用可能時間、障害時の許容範囲が数値または確認可能な条件になっている。
- 対象端末・利用場所・通信不可時・アクセシビリティ配慮がある。
- 問い合わせ、教育、運用監視、障害連絡、変更管理、責任分担がある。

### G10 受入・導入

- 各必須機能に `AC-xxx` が1件以上結び付いている。
- 受入条件は前提、操作・出来事、期待結果、確認者、証拠を含む。
- 通常、未入力、誤入力、権限外、差し戻し、通信不可等を必要に応じて試験できる。
- 試用対象、合否判定者、導入手順、旧手順併用、問題時に戻す条件がある。

### G11 追跡・合意

- 問題 → 目標 → 業務 → 機能要件 → 根拠 → 受入条件がIDで追跡できる。
- 仮説と確認済み事実が混ざっていない。
- 未解決事項には影響、責任者、確認方法、期限、着手可能範囲がある。
- 版、変更履歴、業務・制度・情報管理・最終承認者がある。

## エンジニアに決めてもらう事項との境界

要件ヒアリングで特定技術を勝手に決めない。プログラミング言語、フレームワーク、クラウド製品、データベース製品、ネットワーク構成等は、事業側の制約がない限り `技術設計で決定` と記載する。

ただし、選定に必要な事業条件は確定させる。例：利用端末、保存場所の制約、既存契約、接続対象、利用規模、応答時間、保存年数、予算・期限、社内標準、運用担当者。

## 最終監査

出力直前に次を反証する。

1. エンジニアが「誰が」「いつ」「何を」「どうなれば完了か」を推測する箇所はないか。
2. 必須機能に正常系だけでなく、重要な例外と失敗時の扱いがあるか。
3. 要件と受入条件が1対0になっていないか。
4. 未確認の制度・現行仕様・数値を一般論で埋めていないか。
5. 事業側の決定と、技術設計で決めることを混同していないか。
6. 個人情報、外部送信、AI、請求判断に人の責任境界があるか。
7. 文書状態が実際の完成度と一致しているか。

1件でも重大な欠落があれば `ENGINEERING_READY` にしない。回答者が対話継続を許可している場合は、最も影響が大きい不足を平易な1問へ変換してヒアリングを続ける。
